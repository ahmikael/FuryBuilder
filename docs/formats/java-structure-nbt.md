# Java structure NBT (`.nbt`) format adapter

Status: implemented for Minecraft Java 1.21.4 (`DataVersion` 4189), first export target
per ADR-007. Code: `crates/world-io` (`nbt.rs`, `structure.rs`, `java_structure.rs`,
`exchange.rs`).

## Scope

A Java structure file stores a bounded block region for the structure block, `/place
template`, datapacks and structure-aware editors. FuryBuilder uses it as an interchange
format, never as a project store. FuryBuilder-only metadata (objects, build DSL, undo
history, scene graph, editor state, source provenance) is **not** representable and is
never claimed to be exported.

The adapter handles block states and their properties/orientations. It does not model
entities, block entities, loot tables, processors or structure metadata beyond the schema
below.

## Schema

The root is a gzip-compressed big-endian NBT compound. FuryBuilder reads and writes:

| Tag | Type | Meaning |
|---|---|---|
| `DataVersion` | Int | Target Minecraft data version. FuryBuilder writes `4189` and refuses other versions on strict import. |
| `size` | List\<Int\> (3) | Region size `[x, y, z]`, each `1..=1024`; volume `<= 1,000,000`. |
| `palette` | List\<Compound\> | 1..=4096 entries. Each entry has `Name` (String) and optional `Properties` (Compound of String→String). |
| `blocks` | List\<Compound\> | Sparse non-air positions. Each entry has `state` (Int palette index) and `pos` (List\<Int\> of 3 local coordinates). |
| `entities` | List\<Compound\> or empty List\<End\> | Read for compatibility checks; never modeled or written with content. Export writes an empty list. The official game uses `TAG_End` for an empty list, which is accepted. |
| `author` | String | Written as `FuryBuilder`; preserved on read when present. |

Unknown root, palette or block keys are collected as warnings during preview and cause a
strict import to fail rather than silently dropping them. Block-entity payloads
(`blocks[].nbt`) are counted and treated the same way. Missing positions are air, the Java
structure convention; export stores only non-air positions.

## Block states and orientations

Palette entries are converted through `world_domain::BlockState`, so the exact namespaced
id and property map are preserved. Examples:

- `minecraft:oak_stairs[facing=west,half=top,shape=straight,waterlogged=false]`
- `minecraft:chest[facing=north,type=single,waterlogged=false]`

Property order is canonicalized by `BTreeMap`; two equal states always encode identically.
Orientation is therefore a property, not a separate field, matching Minecraft's own
format. Imported states outside FuryBuilder's palette catalogue are preserved verbatim in
the world (the catalogue is a UI convenience, not the authoritative block list).

## Determinism and verification

- `write_java_structure` sorts blocks by `pos`, uses canonical compound key order and a
  fixed gzip encoder configuration. The same structure and author produce byte-identical
  output.
- `prepare_export` captures the region, writes bytes, decodes them with the strict reader,
  compares the semantic structure, and re-encodes to compare bytes before returning.
- `structure_export` writes through `project_store` (temp file + rename), then re-reads the
  published file, checks its SHA-256 and parses it strictly. Success is only reported when
  the file round-trips to the same structure.
- `read_verified_import` parses strictly, re-encodes and re-parses, refusing bytes that do
  not round-trip. Corrupt gzip, truncated NBT, trailing bytes, invalid UTF-8, unknown tags,
  palette/bit-width errors and out-of-bounds positions are hard errors.

## Golden fixture

`crates/world-io/tests/goldens/java-structure-1.21.4.nbt` is an original fixture (no Mojang
assets). It contains two blocks, including a stairs state with all four properties.

- Size: 252 bytes
- SHA-256: `1801cdab7c0b4200266385552a57ae77b81d06b29d57d2892141251e89ad07e5`
- `tests/golden.rs` asserts the exact bytes, parses them, verifies every property and
  re-encodes them byte-identically. It also proves corruption/truncation is rejected.

The fixture was generated by `crates/world-io/examples/make_golden.rs`; the example is a
development utility and is not part of the application.

## Limits

| Limit | Value |
|---|---|
| Compressed NBT upload | 32 MiB over IPC, 256 MiB in the codec |
| Decompressed NBT | 64 MiB |
| NBT depth | 64 |
| Collection length | 8,000,000 elements |
| Structure axis | 1,024 |
| Structure volume | 1,000,000 blocks |
| Palette entries | 4,096 |
| Operation batch | 1,000,000 blocks (`MAX_OPERATION_BLOCKS`) |

All lengths are checked against remaining bytes before allocation. Hostile files cannot
force unbounded memory use through a declared length alone.

## Import flow

1. The UI reads a user-picked file locally and sends base64 bytes over IPC (no filesystem
   path is accepted). The backend caps the compressed size and decodes.
2. `structure_import_preview` parses structurally and returns size, volume, palette counts,
   entity/block-entity counts, unknown tags, target version and warnings. It never modifies
   a world.
3. Strict import refuses a different `DataVersion`, entities, block entities or unknown
   tags: the UI shows **Import blocked** instead of dropping data.
4. `structure_import_project` creates an Empty project, copies the original bytes into the
   immutable `source/files/` layer with a SHA-256, inserts the structure at the requested
   origin through one audited batch operation, saves revision 2 and opens the project.
5. `structure_insert` inserts into the open project as unsaved work, preserving the
   project's existing source provenance. Undo remains available as one batch operation.

Vertical placement is validated against the target dimension (`-64..=319` Overworld,
`0..=127` Nether, `0..=255` End).

## Export flow

1. The UI chooses a dimension and either the current box selection or the content bounds
   (all non-air blocks, computed from stored sections only).
2. `structure_export_preview` returns size, volume, non-air/stored blocks, palette, byte
   size, SHA-256, target versions, warnings and the proposed path under the project's
   `exports/` folder. Unsaved revisions are called out.
3. `structure_export` re-captures the world, refuses to proceed if the checksum differs
   from the preview, publishes atomically, re-reads and verifies the file, and returns the
   final path, checksum and `verified: true`.
4. Export never overwrites an existing file: a numeric suffix is added under `exports/`.

## Interoperability status

- The golden fixture and the two game-saved fixtures are parsed by FuryBuilder's strict
  reader. See `docs/testing/test-matrix.md`.
- An official Minecraft 1.21.4 server loaded output from both the core export example and
  the real Tauri IPC export. The procedure and exact results are in
  `docs/testing/minecraft-structure-check.md`. It requires a user-supplied Java 21 runtime,
  server JAR and already accepted EULA; FuryBuilder neither accepts the EULA nor downloads
  files during this check.
- The Tauri probe exercised the real IPC bridge but used recorded commands rather than a
  human click-through; the UI contract is covered separately by component tests.

## Known limitations

- Only Java structure `.nbt` is implemented in M6. Sponge `.schem` v3 is the second target
  (ADR-007) and is not yet available.
- Entities and block entities are refused on import and never written on export.
- The format has no concept of dimensions, biomes, ticks or project history.
- Import creates a new Empty project or inserts into the current project; it does not
  merge a source world save.
